# Функциональность проекта для проектирования backend API

Документ составлен по текущему коду `cps-console`, `cps-desktop` и `cps-core`.
Это перечень существующих пользовательских сценариев и их правил, на основе
которого далее проектируются эндпоинты, DTO, доступ к данным и валидация.
Реализованные HTTP-маршруты, DTO и передача аргументов сервисов описаны
в [контракте API](backend-api.md). Таблицы ниже сохраняют результаты анализа
консольного и Desktop-приложения.

В таблицах «Да» означает наличие доступного действия в приложении.
Наличие метода в `cps-core` или неиспользуемого редактора отдельно отмечается
и не приравнивается к работающему пункту интерфейса.

## 5. Остатки и доступность товаров

| ID | Функция | Консоль | Desktop |
| --- | --- | --- | --- |
| STOCK-01 | Получить физические остатки товара по складам | Да | Просмотр в разрезе выбранного склада, см. WAREHOUSE-03 |
| STOCK-02 | Установить абсолютное количество товара на складе: создать запись или изменить существующую | Менеджер | Да; роль не проверяется |
| STOCK-03 | Удалить запись о товаре на складе | Менеджер | Отдельного действия нет |
| STOCK-04 | Рассчитать доступное для заказа количество с учётом резервов | Проверка при сохранении заказа | Показ в форме заказа и проверка при сохранении |

Правила:

- Пара «товар — склад» уникальна; товар и склад должны существовать.
- Остаток — целое число от `0` до `2147483647`. Установка количества заменяет
  значение, а не прибавляет его к текущему остатку.
- Физический остаток товара — сумма количества на всех складах.
- Заказы в статусах `CREATED` и `APPROVED` резервируют товар.
- Доступное количество = физический остаток минус резервы активных заказов,
  с нижней границей `0`. При редактировании заказа его собственный резерв
  исключается из расчёта.
- Нельзя уменьшить или удалить остаток, если суммарного физического количества
  после операции станет недостаточно для действующих резервов.
- Доставка списывает физический остаток с одного или нескольких складов.
  Повторная установка статуса `DELIVERED` не списывает товар повторно.
- Проверка доступности и изменения выполняются в транзакции с блокировками
  товаров, чтобы одновременные заказы не резервировали одну и ту же единицу.

Источники: [StockEditorController](../cps-desktop/src/main/java/com/team/corporate/desktop/controllers/modals/StockEditorController.java),
[InventoriesServiceImpl](../cps-core/src/main/java/com/team/corporate/core/services/impls/InventoriesServiceImpl.java),
[OrderStock](../cps-core/src/main/java/com/team/corporate/core/services/impls/OrderStock.java).

| ORDER-08 | Удалить позицию из собственного созданного заказа | Да | Удаление из корзины до создания; код редактирования сохранённого заказа не подключён |
| ORDER-09 | Изменить или очистить примечание собственного созданного заказа | Да | Да, на странице общих заказов |
| ORDER-10 | Получить общий список заказов | Менеджер | Обе роли |
| ORDER-11 | Найти общие заказы по ID/примечанию, пользователю, статусу и диапазону суммы | Нет | Да |
| ORDER-12 | Отсортировать общий список по дате или сумме в обоих направлениях | Нет | Да |
| ORDER-13 | Сменить статус заказа | Менеджер | Менеджер |
| ORDER-14 | Удалить заказ вместе с позициями и записями его аудита | Нет | Да; роль и владелец не проверяются |

Правила создания и редактирования:

- Новый пользовательский заказ создаётся в статусе `CREATED` и принадлежит
  текущему пользователю. Выбора другого владельца в формах нет.
- Нужна хотя бы одна позиция; каждый товар должен существовать.
- Количество одного товара — от `1` до `100000`; при создании и полной замене
  состава повторяющиеся товары объединяются, а их суммарное количество
  проверяется по тому же ограничению.
- Цена новой позиции берётся из каталога. Сумма позиции = цена покупки ×
  количество; сумма заказа = сумма всех его позиций.
- При сохранении состава существующие позиции сохраняют цену покупки,
  новые позиции получают текущую цену каталога.
- Менять состав и примечание через пользовательские операции может только
  владелец и только в статусе `CREATED`, в том числе если владелец — менеджер.
- В консольном изменении позиции количество `0` означает удаление позиции;
  последнюю позицию удалить нельзя.
- Заказ и его состав сохраняются атомарно: при ошибке не должно оставаться
  частичного заказа или изменённого резерва.

Текущая логика переходов статуса в `changeStatus`:

| Текущий статус | Допустимые другие статусы | Условия |
| --- | --- | --- |
| `CREATED` | `APPROVED`, `DELIVERED`, `CANCELLED` | Доставка проверяет доступность и списывает остатки |
| `APPROVED` | `CREATED`, `DELIVERED`, `CANCELLED` | Доставка проверяет доступность и списывает остатки |
| `CANCELLED` | `CREATED`, `APPROVED`, `DELIVERED` | Повторно проверяется наличие товаров; при доставке выполняется списание |
| `DELIVERED` | Нет | Изменение на другой статус запрещено |

Смену статуса выполняет менеджер. Повторная установка текущего статуса —
операция без изменений и без новой записи аудита. При фактической смене
сохраняются заказ, автор изменения, старый/новый статус и время.
Отмена снимает резерв, но не увеличивает физический остаток.

[MyOrdersController](../cps-desktop/src/main/java/com/team/corporate/desktop/controllers/pages/MyOrdersController.java),
[OrdersController](../cps-desktop/src/main/java/com/team/corporate/desktop/controllers/pages/OrdersController.java),

Экспорт создаёт отдельную папку с восемью файлами: `users.csv`,

нет. В `cps-core` есть методы выборки аудита по заказу/автору/статусам, но
это возможность сервисного слоя, а не подтверждённый пользовательский сценарий.
Способ передачи CSV по HTTP предстоит определить: текущий выбор локальной
папки не задаёт контракт скачивания с сервера.

## 10. Общая валидация и различия клиентов

| Данные | Правила в `cps-core` | Дополнительные ограничения Desktop |
| --- | --- | --- |
| Имена, названия, артикул | Обязательные строки непустые после `strip()`; максимум 255 символов до удаления пробелов | Артикул максимум 40 символов и шаблон `[A-Z0-9]{3,10}(-[A-Z0-9]{3,10})*`; ввод переводится в верхний регистр |
| Примечание, адрес | Необязательные строки, максимум 255 символов; пробелы по краям удаляются | Формы позволяют очистить поле |
| Управляющие символы | Запрещены ISO control, кроме `\n`, `\r`, `\t` | Используются общие проверки текстового ввода |
| Цена | От `0` до `99999999.99`; не более двух десятичных знаков после удаления конечных нулей; хранение с масштабом 2 | Форма товара требует цену строго больше `0`; консоль допускает `0` |
| Количество в заказе | Целое, `1..100000`; также проверяются объединённые количества одного товара | Показ доступного остатка и запрет добавить сверх него |
| Складской остаток | Неотрицательный `int` | Целое неотрицательное значение |
| Роль и статус | Только значения `UserRole` и `OrderStatus` | Выбор из фиксированного списка |
| Ссылки на сущности | Существование товара, категории, склада, пользователя и принадлежность позиции заказу проверяются сервисами | Выбор из загруженных списков |

Источник: [EntityValidation](../cps-core/src/main/java/com/team/corporate/core/utils/EntityValidation.java)
и редакторы Desktop. Эти различия нужно разрешить в контракте API, прежде
чем переносить ограничения в HTTP DTO.

## 11. Решения перед проектированием эндпоинтов

Это обнаруженные расхождения текущей реализации, а не уже выбранные правила API.

1. **Права на каталог, категории, склады и остатки.** Консоль разрешает
   изменения менеджеру; Desktop допускает их для обеих ролей. В этих сервисах
   нет проверки действующего пользователя. Нужна единая матрица прав API.
2. **Просмотр и удаление общих заказов.** В Desktop обе роли видят все заказы
   и могут удалять чужие; сервис удаления не проверяет владельца, роль
   или статус. Можно удалить даже доставленный заказ, вместе с аудитом,
   без возврата физического остатка. Политику нужно выбрать отдельно.
3. **Редактирование сохранённого заказа в Desktop.** `OrderEditorController`
   поддерживает замену состава, но `OrderEditorRequest.forEdit` и `EDIT_ORDER`
   не вызываются страницами. Полноценное редактирование есть в консоли
   и в `cps-core`; нельзя описывать Desktop-форму как уже доступный сценарий.
4. **Смысл количества в сводке заказа.** «Мои заказы» считает число строк,
   а общий список — сумму количества единиц. Для API следует дать этим
   величинам разные имена.
5. **Валидация товара.** Нужно выбрать правила цены, формата артикула и
   обязательности категории с учётом отличий Desktop, консоли и модели БД.
6. **Переходы статусов.** Сейчас возможны доставка без предварительного
   одобрения и повторное открытие отменённого заказа. Более строгого процесса
   согласования в текущем коде нет.
7. **Идентификация пользователя.** Текущий вход по имени и локальные сессии
   не определяют способ аутентификации HTTP-запросов.
8. **Поиск, сортировка и даты.** Desktop фильтрует загруженные списки в памяти;
   готовых запросов DAO для всех этих фильтров нет. При переносе в API нужно
   определить параметры, порядок сортировки, границы диапазонов, часовой пояс
   дат и необходимость пагинации.
9. **Экспорт и аудит.** Следует определить формат выдачи файлов по HTTP
   и необходимость отдельного просмотра истории. Ручной CRUD аудита
   не следует из существующих интерфейсов.

## 12. Как использовать перечень для backend

Для каждого выбранного сценария по его ID далее фиксируются:

1. HTTP-метод, маршрут и допустимые параметры поиска/сортировки.
2. Роли, правило владения ресурсом и источник текущего пользователя.
3. DTO запроса/ответа, обязательные поля и единая валидация.
4. Вызов бизнес-сервиса, граница транзакции и требуемые запросы к данным.
5. Ответы при успехе, отсутствии сущности, конфликте данных и отказе в доступе.
6. Проверки бизнес-правил, включая резервирование, доставку и аудит.

Доступ к данным уже представлен интерфейсами `*Repository` и Hibernate-
реализациями в [cps-core/repositories](../cps-core/src/main/java/com/team/corporate/core/repositories).
При реализации HTTP нужно оценить их переиспользование и добавить недостающие
запросы для фильтров и агрегатов. DAO отвечает за доступ к данным; DTO задаёт
формат HTTP, а проверка остатков и переходов статуса остаётся в сервисном слое.
Количество эндпоинтов определяется сценариями, а не количеством таблиц.
